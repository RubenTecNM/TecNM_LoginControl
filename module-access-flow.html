LoginControl / Diseño de integración

Un login. Acceso a otras aplicaciones.

Diagrama UML de secuencia del flujo propuesto. El único inicio de sesión ocurre en LoginControl. Servicio Social recibe un código temporal, consulta al backend central y crea su sesión con la identidad validada.

Flujo con correlación automática aprobada; todas las peticiones usan HTTPS.Petición o acciónRespuesta

Si no tiene permiso

LoginControl rechaza el lanzamiento. No genera código ni navega al módulo. Una sesión inválida devuelve 401; acceso no habilitado, 403.

Si el canje es inválido

Clave inválida, código vencido, usado o de otro módulo: se rechaza sin devolver identidad. También se revisa que la asignación siga activa. El módulo no crea sesión.

Claves y sesiones separadas

La API key es exclusiva del módulo y nunca viaja al navegador. No se comparte la clave de firma JWT. Deshabilitar una asignación bloquea nuevos ingresos; no cierra sesiones externas existentes.

Leer el flujo en texto
  1. Entra a LoginControl e inicia sesión. Único formulario de login: Google o Microsoft.
  2. GET /api/modules. Cookie de sesión central.
  3. Consulta módulos activos asignados. Usuarios, módulos y asignaciones.
  4. Devuelve accesos vigentes. Respuesta.
  5. Muestra módulos en dashboard. Respuesta.
  6. Selecciona Servicio Social. Usuario autenticado.
  7. POST /api/modules/{id}/launch. Cookie central y origen exacto.
  8. Comprueba acceso y guarda ticket temporal. browser_confirmed=false; hash y vencimiento de 60 segundos.
  9. Confirma intento registrado. Respuesta.
  10. Devuelve URL registrada con ticket. Respuesta.
  11. GET /acceso/?ticket=TICKET. Primera llegada al módulo.
  12. Establece cookie de correlación y redirige. State aleatorio propio; redirección automática.
  13. GET /api/modules/authorize?ticket=...&state=.... El navegador lleva su cookie de LoginControl.
  14. Valida sesión del mismo usuario y permisos. Consume ticket; genera código confirmado en transacción.
  15. Confirma código canjeable de un uso. Respuesta.
  16. 302 a URL registrada con code y state. Referrer-Policy: no-referrer.
  17. GET /acceso/?code=...&state=.... Cookie de correlación del propio módulo.
  18. Compara state con su cookie y la elimina. Sin coincidencia: rechaza sin canjear.
  19. POST /api/modules/exchange. Authorization: Bearer API_KEY · JSON: { moduleId, code }.
  20. Valida clave, código confirmado y permiso actual. Código correcto, vigente y sin uso; consume atómicamente.
  21. Devuelve identidad y confirma consumo. Respuesta.
  22. 200 con user: ID, nombres, apellidos y correos. Respuesta.
  23. Crea su sesión propia. No solicita otro login.
  24. Cookie de sesión y redirección a URL limpia. Respuesta.
  25. Abre aplicación con cookie propia. Sin parámetros temporales.
  26. Muestra Servicio Social. Respuesta.
Lectura de arriba hacia abajo. En pantallas pequeñas, desplaza el diagrama horizontalmente. Todas las comunicaciones HTTP del flujo usan HTTPS. Este documento describe el intercambio; el receptor debe comparar state con su cookie antes de canjear el código.
